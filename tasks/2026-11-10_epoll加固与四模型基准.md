### ⏰ 09:20–09:40 · 修 A + B：`~EpollServer` 空指针与双重 close（20 min）**← P0**

这是**今天唯一"能让进程直接崩掉"的缺陷**，排在最前面。

现状（`Epoll_server.hpp:29-33`）：
```cpp
~EpollServer(){
    if (_epoll.get()->get_fd() >= 0){
        ::close(_epoll.get()->get_fd());
    }
}
```

两个独立问题：

1. **`_epoll` 可能是 `nullptr`**。它只在 `epoll_init()` 里赋值，而 `epoll_init()`
   只在 `run_loop()` 里调用。构造后不 `start()` 就析构 → 空指针解引用。
   实测：`int main(){ EpollServer s(6398); return 0; }` → `Segmentation fault`，exit=139。
2. **`close` 了两次**。`_epoll` 是 `unique_ptr<Epoll>`，`~Epoll` 的析构里已经
   `close(_epoll_fd)`。strace 铁证：`close(4)=0` → `close(4)=-1 EBADF`。

- [x] **修法：整个析构函数删掉**（`close` 的唯一 owner 是 `~Epoll`）
- [x] 如果确实要在析构里做事，必须写成 `if (_epoll && _epoll->get_fd() >= 0)`
- [x] **验收 1**：`strace -f -e trace=close,epoll_create1` 观察 SIGINT 退出，
      必须只有**一次** `close(4)`，不再出现 `EBADF`
- [x] **验收 2**：`int main(){ EpollServer s(6398); return 0; }` 必须 exit=0，
      不再段错误
- [x] **验收 3**：`./test/test_04_epoll.sh --no-build --all` 仍 7/7 绿

> ⚠️ 纪律：一次只改一个缺陷。A 和 B 在同一个函数里，一起改、一起验，但**验收 1 和 2
> 都要单独跑一遍**，不要只看 test_04 绿了就算完 —— test_04 从来不测析构路径。

### ⏰ 09:40–10:00 · 修 F：`epoll_init()` 的 `fcntl` 返回值（20 min）

现状：
```cpp
int flags = fcntl(_listen_fd,F_GETFL);       // 失败返回 -1，没检查
fcntl(_listen_fd,F_SETFL,flags|O_NONBLOCK);  // 失败返回 -1，没检查
```

`F_GETFL` 失败时 `flags = -1 = 0xFFFFFFFF`，`flags | O_NONBLOCK` 还是
`0xFFFFFFFF`，`F_SETFL` 会把 fd 的状态标志位全部打开（含 `O_APPEND`、
`O_ASYNC` 等）。**监听 fd 变成异步信号驱动的，行为完全不可预测。**

- [x] `F_GETFL` 失败 → 打印 `strerror(errno)` + 返回 `false`
- [x] `F_SETFL` 失败 → 同上
- [x] **验收**：gdb 里 `p (int)fcntl(this->_listen_fd, 3, 0)` 应为 `0x802`
      （`O_RDWR|O_NONBLOCK`）

### ⏰ 10:30–11:00 · 修 C：`wbuf` 上限（30 min）**← P1 内存炸弹**

现状：`append_wbuf` 无任何上限。实测 64 MB 载荷 + 客户端憋 8 秒不读：

```
启动 RSS = 3,764 KB
峰值 RSS = 67,344 KB     ← 涨了 63.5 MB
```

> ⏸ **今天暂缓** —— 用户原话：「send 这里由于我测试未发现异常先不改」。
> 已实测确认的边界（**记进 note，不能忘**）：
> - `never-read` 场景下 wbuf **永久滞留 5.96 MB/连接**，1000 条慢客户端 = 6 GB
> - `slow-read` 场景 wbuf 峰值 5.94 MB，`flush` 的 early return 让它只进不出
> - 本机 loopback 测不出崩溃，但**公网高延迟链路 + 慢客户端**必然放大

- [ ] `EpollServer` 加常量 `static constexpr size_t kMaxWbufSize = 1 << 20;`（1 MB）
- [ ] `flush` 里 append 之前检查：
      ```cpp
      if (conn_ptr->wbuf_size() + __n > kMaxWbufSize) {
          std::cerr << "wbuf overflow fd=" << fd << '\n';
          del_and_close(fd);
          return;
      }
      ```
- [ ] **注意检查时机**：必须在 `append` **之前**判断，不能 append 完再判断
      （那样已经吃进内存了）
- [ ] **验收**：复现今天的实验，峰值 RSS 必须被压在 ~2 MB 以内，且客户端收到
      "连接被断开"而不是 OOM
- [ ] 现成的复现工具（`test/handle_write_trigger.py` 已写好，直接用）：
      ```bash
      python3 test/handle_write_trigger.py --mode=slow-read   # wbuf 峰值 5.94 MB
      python3 test/handle_write_trigger.py --mode=never-read  # 永久滞留 5.96 MB
      ```

**产出对比表（16:05 实测，nproc=4，Debug，本机 loopback）：**

**场景 1 · hold**（200 条空闲连接 × 4 秒，只连不发）

| 模型 | 状态 | 线程数 | RSS (KB) | 建连成功 |
|---|---|---|---|---|
| base | OK | **1** | 3708 | 200 |
| thread | OK | **201** | 6544 | 200 |
| pool(4) | OK | 5 | 3988 | 200 |
| **epoll** | OK | **1** | **3796** | 200 |

> `thread` = 1 主线程 + 200 连接线程。`epoll` 用 1 个线程扛下同样 200 条连接，
> RSS 还比 thread 少 2.7 MB（没有 per-thread 栈）。**这是 epoll 最硬的价值。**
>
> ⚠️ base 这里显示 `OK / 200` 具有误导性：客户端 200 条连接都建立了（内核 accept
> 队列兜着），但 base 只会**串行**处理它们，4 秒内一条都没服务完。这个场景测的是
> 「能维持多少连接」，不是「能服务多少连接」，所以 base 在这一列不算输 —— 它的
> 代价体现在场景 2 的线性增长上。

**场景 2 · latency**（20 连接 × 300 消息 × 256 B，严格 ping-pong）

| 模型 | 状态 | msg/s | p50 (ms) | p99 (ms) |
|---|---|---|---|---|
| **base** | OK | 8202 | **0.107** | **0.235** |
| **thread** | OK | **11865** | 1.621 | 2.651 |
| pool(4) | OK | 11520 | 0.325 | 0.499 |
| epoll | OK | 10922 | 1.785 | 2.514 |

> **这个场景 epoll 不是最快的，必须诚实写出来。** 两个反直觉但正确的事实：
>
> 1. **base 的 p50 最低（0.107 ms）、p99 最低（0.235 ms）。** 因为它只服务一条
>    连接时没有任何上下文切换、没有锁、没有事件循环 —— 单连接的最优解就是它。
>    它的 p50 在 conns=1/4/20 下分别是 0.099/0.117/0.114，**完全不变**，因为
>    它同一时刻只处理一条连接，20 条连接的延迟是「排队 + 串行」，不是并发。
> 2. **epoll 的 p50 比 thread 还差（1.785 vs 1.621）。** 单线程 reactor 要在
>    20 条连接之间轮转，每条连接都要走一遍 epoll_wait + 状态机。thread 模型
>    每连接独占线程，RTT 路径最短。
>
> **结论：epoll 的价值不在延迟，在并发规模 + 抗 pipeline。**

**场景 3 · pipeline**（20 连接 × 2000 消息 × 4096 B = **160 MB**，写完再读）

| 模型 | 状态 | msg/s | p50 (ms) | p99 (ms) | recv |
|---|---|---|---|---|---|
| base | OK | 15869 | 1351.0 | 1940.4 | 40000 |
| thread | ⚠️ | 26137 | 920.6 | 1324.7 | 40000 |
| pool(4) | OK | 16378 | 1404.7 | 1825.6 | 40000 |
| **epoll** | OK | **30669** | **823.6** | **1210.8** | 40000 |

> **epoll 1.9× base / 1.87× pool / 1.17× thread。** 这是它的主场。
>
> ⚠️ **thread 的数字带星号**：15 次连跑 15 次通过（avg 30861 msg/s），但摸底阶段
> 曾 5 次连跑 5 次卡死。**这是一个概率性死锁，触发率约 4%**（约 1/25），一旦触发
> 就是永久卡死（直到 timeout）。所以 thread 这一行不能当成稳定吞吐看。
>
> **死锁根因（`ss` + `ps -L` 现场抓到）：双向缓冲互锁。**
> ```
> 服务端: ESTAB Recv-Q=29760  Send-Q=3621568
> 客户端: ESTAB Recv-Q=102016 Send-Q=3415872
> 服务端线程停在 wait_woken ← 阻塞在 send()
> ```
> 客户端 `write` 完 8 MB 才去 `read`，服务端 `send_wbuf` 是阻塞 `send`；
> 服务端发送缓冲填满 → 阻塞；客户端 `drain()` 也在等 → 两边都在写，谁都不读。
>
> 为什么 pool 不死锁：只有 4 个 worker，**同时阻塞的连接数上限是 4**，
> 其余连接的数据堆在内核缓冲里，反而给客户端腾出了读取窗口。
> 为什么 epoll 不死锁：wbuf + `EPOLLOUT`，服务端**永不阻塞**。
>
> 📌 这个死锁按你的决定**本轮不修**，单独处理。表里如实标 ⚠️。

**一句话总结（README §五 素材）：**

| 你想要什么 | 选谁 | 证据 |
|---|---|---|
| 单连接极致延迟 | base | p50 0.107 ms，比 epoll 快 16× |
| 中等并发低延迟 | pool(4) | p50 0.325 ms，1 万连接以内够用 |
| 海量连接 | **epoll** | 200 连接 1 线程 3.7 MB，thread 要 201 线程 |
| 大流量 pipeline | **epoll** | 30669 msg/s，1.87× pool，且**永不阻塞** |
| 别用 | thread | 200 连接 201 线程；pipeline 4% 概率死锁 |

## 关键陷阱备忘（今天最容易翻车的三处）

### 陷阱 1：`mod` 默认值不能单独改

```cpp
// 只改这一行 ↓ 会让数据卡死在 wbuf 里
bool mod(int fd, uint32_t events = EPOLLIN);
```

必须先改两个调用点，再改默认值。顺序反了会出现"测试绿、数据不发"的静默故障。

### 陷阱 2：`wbuf` 上限必须在 append 之前判断

```cpp
conn_ptr->append_wbuf(data, n);                    // ❌ 已经吃进内存了
if (conn_ptr->wbuf_size() > kMaxWbufSize) ...
```

### 陷阱 3：`_woff` 改造后 `clear_wbuf` 要一起改

```cpp
void clear_wbuf(){ _wbuf.clear(); }        // ❌ _woff 还停在旧值
void clear_wbuf(){ _wbuf.clear(); _woff = 0; }   // ✅
```

漏了这条，`clear` 之后再 `wbuf_empty()` 会返回 `false`，然后 `wbuf_data()`
返回 `_wbuf.data() + 旧 _woff` → **越界读**。
