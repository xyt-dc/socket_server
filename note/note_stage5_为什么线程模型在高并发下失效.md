# 零、结论先行

一句话：

> **线程是"让一个执行流等另一个资源"的工具，不是"同时处理很多连接"的工具。**
> **用线程去应对 IO 等待，等于用最贵的资源去等最便宜的事。**

三条核心结论：

1. **thread-per-connection 的并发度是 O(连接数) 个线程** —— 1 万连接就是 1 万个线程，
   线程栈内存、调度开销、上下文切换在千级连接时就已经不可接受。
2. **线程池把线程数从 O(连接数) 降到 O(worker 数)，但代价是并发度也降到 O(worker 数)** ——
   线程爆炸换成了**静默的服务不可用**，而且更隐蔽（没有报错，没有 CPU 飙高）。
3. **两者的共同病因是阻塞 `recv()`**。不把 socket 改成非阻塞，
   无论怎么调度线程，都只是把"线程被一条连接焊死"这件事换个位置重演。

**reactor 解决的唯一问题是：让一个线程能同时"看住"上万个 fd，
从而让"任务"从"整个连接的生命周期"变成"一次读写事件"。**

# 一、三种模型的真实差异

## 1.1 代码上的差异其实只有一处

得益于 `TcpServerBase` 的 Template Method 设计，`start()`
（`create_socket → set_reuse_addr → do_bind → do_listen → run_loop`）
是写死的，三个模型**只覆写 `run_loop()`**：

```cpp
// tcp_server.hpp —— 唯一纯虚函数，唯一的接缝
virtual void run_loop() = 0;
```

| 模型 | `run_loop()` 里干的事 | 每条连接占用的资源 |
|---|---|---|
| `ThreadPerConnServer` | `accept` → `new std::thread` → `detach` | **1 个线程** |
| `ThreadPool_server` | `accept` → `_Pool.submit(长任务)` | **0 个线程，但占 1 个 worker** |
| `EpollServer`（待写） | `epoll_wait` → 分发就绪事件 | **1 个 fd + 一点内存** |

**代码只差 20 行，架构差了一个数量级。** 这就是"接缝选对了"的价值。

## 1.2 资源账（这是关键）

`【实测】` 本机环境：

```
$ nproc       → 4        （4 核，所以 workers 取 4）
$ ulimit -s   → 8192     （8 MB 虚栈/线程）
$ ulimit -n   → 1048576  （单进程 fd 上限 100 万，epoll 能吃满）
```

| 连接数 | thread-per-conn 线程数 | 线程栈虚拟内存 `【推算】` | pool(workers=4) 线程数 |
|---|---|---|---|
| 20 | 21 `【实测】` | 168 MB | 5 `【实测】` |
| 1,000 | 1,001 | **8 GB** | 5 |
| 10,000 | 10,001 | **80 GB** | 5 |
| 100,000 | 100,001 | **800 GB** | 5 |

注意这只是**栈的虚拟地址空间**，还没算：

- 内核里每个线程的 `task_struct`（约 8–16 KB 实打实的内核内存）
- glibc 的线程本地存储、guard page
- **调度器要在这么多 runnable 实体之间做选择**

`【推算】` 10,000 线程时仅内核数据结构就吃掉 100–200 MB，
而 epoll 方案里再多的连接也只占 1 个 `epoll_event`（12 字节）+ 连接对象。

# 二、实测：三个缺陷的完整证据

跑法：`./test/test_03_pool_starvation.sh`

测试脚手架三角：

- `test/bench_server.cpp` —— 压测专用服务端入口，`--server=thread|pool` 运行时切换模型。
  单独放 `test/` 下，**`src/main.cpp` 一行没动**。
- `test/bench_client.py` —— asyncio 客户端。选它是因为 **2000 连接只占 1 个客户端线程**，
  这样测出来的数字能归因到服务端，而不是客户端自己的调度开销。
- `test/test_03_pool_starvation.sh` —— 编排 + 断言。

## 实验 A：worker 占满后，新连接彻底饿死

**场景**：`--workers=2`，先建 2 条"只连不发"的连接占死 worker，
再建第 3 条连接发 3 条 64 字节消息，看有没有 echo。

```
【实测】
  pool  模型：第 3 条连接收到 0 条 echo，errors=1
  thread 模型：第 3 条连接收到 3 条 echo

  ✓ pool 模型复现饿死：worker 被占满后新连接无响应
  ✓ thread 模型正常服务第 3 条连接（对照成立）
```

**这个现象最可怕的地方在于它的沉默**：

服务端的日志里，这第 3 条连接是**完全成功**的：

```
accept() 返回 fd      ✅ 成功
_clients.emplace(fd)  ✅ 成功
_Pool.submit(...)     ✅ 成功（队列没满）
```

然后就没有然后了。没有错误日志、没有拒绝计数、CPU 没有升高、内存没有涨。
**客户端只能看到一个 5 秒超时。**

对比"线程爆炸"：那种情况下你能看见 CPU 100%、能看见 `std::bad_alloc`、
能看见"无法创建线程"。**至少有症状。**

而这里是**静默的服务不可用** —— 生产环境里这种 bug 能活好几个月。

## 实验 B：队列满只能拒绝新连接，无法对已有连接限流

**场景**：`--workers=1 --queue-cap=1`，占满 worker，再塞满队列，第 3 条连接：

```
【实测】
  { "conn_ok": 1, "recv": 0, "errors": 0, "eof_early": 1, ... }
  ✓ 第 3 条连接被服务端主动 close（eof_early=1, recv=0）
```

对应代码（`thread_pool_server.hpp`）：

```cpp
bool acc = _Pool.submit([this, fd](){ handle_client_read(fd); });
if (!acc) {
    _clients.erase(fd);
    ++_reject_count;
    close(fd);              // ← 唯一的背压手段：踢掉新的
}
```

**能拒绝新来的，但动不了已经在跑的。** 具体后果：

如果一条连接连上来之后开始狂发数据（比如上传 10 GB），
它会一直占着一个 worker 做 `recv`，直到发完为止。协议里**没有"暂停"的能力**：

- 没法告诉它"慢点"
- 没法把数据先收进缓冲区、稍后再处理
- 没法限制它一次能发多少

> **这个设计的最大吞吐能力 = 最慢的那个客户端。**

真正的背压需要"读了但先不处理"的能力 —— 也就是**必须能非阻塞地读**。
阻塞 socket 上你连"读了但处理不了"这个状态都表达不出来。

## 实验 C：线程数与连接数的关系

**场景**：20 条 hold 连接，分别在两种模型下看 `/proc/PID/task` 数量。

```
【实测】
  thread 模型，20 条连接 → 21 个线程
  pool   模型（workers=4），20 条连接 → 5 个线程
```

解读：

```
thread 模型：线程数 = 连接数 + 1        （+1 是 accept 主线程）
pool   模型：线程数 = workers + 1       （与连接数无关）
```

**pool 确实省下了线程。但注意第二行的完整含义**：

> 线程数 5，**并发服务能力也是 4**（不是 20、不是 1000）。

省线程和限并发是同一枚硬币的两面。**参数换不来架构**：
把 `workers` 从 4 调到 1000，就回到线程爆炸；调回 4，就把并发锁死在 4。

## 历史数据：CPU 空转与日志风暴

`【实测】` 来自阶段 2（`note_stage2`）的 EMFILE 治理：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| CPU | 100% | ~0% |
| 日志量（2 秒内） | **580,941 行** | 2 行 |

根因是 `accept` 失败后 `perror` + `continue` —— 一个错误的**紧循环**。
这条数据的意义：**阻塞模型里任何"重试"都会变成忙等**，
因为它唯一能做的等待动作就是"再调一次系统调用"。

## 线程池加速比：2.75x 而非 4x

`【实测】` `lib/thread_pool.hpp` 的 CPU 密集任务测试（4 线程）：

```
线程池总耗时   374 ms
单线程         1027 ms
加速比         2.75x
```

这条数据说明：**即使任务是纯 CPU 密集、完全适配线程池的场景，
4 个线程也只能拿到 2.75 倍。** 差值来自队列锁竞争 + 假共享。

结论：**线程池在它最擅长的场景下都不是线性的**，更不用说用 IO 等待去喂它。

# 三、根因分析：为什么线程救不了

## 3.1 算一笔延迟账

`【推算】` 以典型值估算一次请求的处理链条：

| 环节 | 耗时 | 线程在干什么 |
|---|---|---|
| `recv()` 等数据到达 | **1–100 ms**（取决于 RTT） | **睡眠** |
| 处理业务逻辑 | 1–100 μs | 占用 CPU |
| `send()` 等缓冲区可写 | 10 μs – 100 ms | **睡眠** |
| 合计 CPU 实际占用 | **< 0.1%** | |

也就是说：**一个线程 99.9% 的时间在睡觉。**

上下文切换成本 `【推算】`（现代 x86，含 cache/TLB 污染）：

| 项目 | 耗时 |
|---|---|
| 线程上下文切换 | 2–5 μs |
| 因此损失的 L1/L2 缓存 | 更多（间接成本） |
| 一次业务处理实际需要的 CPU | 1–100 μs |

所以当线程数超过 CPU 核数很多时：

```
线程 A 醒来 → 处理 20μs → 睡
线程 B 醒来 → 处理 20μs → 睡
...
1 万个线程轮流，每次切换 3μs，切到同一个线程要等 1 万 × 20μs = 200ms
```

**延迟被"排队等 CPU"这件事本身放大了。** 这不是线程不够快，
是**线程太多导致每个线程分到的 CPU 时间片变小，而切换成本不变**。

## 3.2 三条不可逾越的硬限制

| 限制 | 数值 | 后果 |
|---|---|---|
| 每进程线程数上限 | 默认约 32,000（受内存限制更早） | 无法支撑 C100K |
| 线程栈 | 8 MB 虚拟 / 几 KB 实占 | 1 万线程 = 80 GB 虚拟内存 |
| `epoll` 无 fd 数量限制 | 受 `RLIMIT_NOFILE`，可调到百万 | **一个线程管百万连接** |

第三条是关键：**fd 是可以很便宜的，线程不是。**
把每个连接绑定到一个线程，等于给每个连接付了线程的价钱。

## 3.3 真正的病根：`recv()` 会阻塞

```cpp
// 这一行的本质：线程主动放弃 CPU，直到内核有数据
ssize_t n = recv(fd, buf, sizeof(buf), 0);
```

阻塞的本质是**线程把自己的调度权交给了这一个 fd**。

于是：

```
线程 ⊂ 连接        （1:1 绑定，无法解开）
```

这个绑定关系是**所有问题的源头**。想让一个线程管多条连接，
唯一的办法就是**让 `recv` 不阻塞**，把"等"这个动作从线程身上剥离出来，
交给一个能同时等很多 fd 的机制。

> **这就是 IO 多路复用的全部动机。**
> 它不解决"数据怎么处理"，只解决"谁来等、怎么等"。

# 四、线程池为什么也没解决问题

这是最容易误解的一节。线程池看起来很对：限制线程数、复用线程、避免创建销毁开销。
但它在本项目里失效了，原因非常具体。

## 4.1 提交的是"长任务"，不是"短任务"

```cpp
// thread_pool_server.hpp
_Pool.submit([this, fd = res_fd.fd]() {
    handle_client_read(fd);          // ← 这个函数在连接的整个生命周期内不返回
});
```

```cpp
void handle_client_read(int fd) {
    char buf[4096];
    while (true) {
        ssize_t n = recv(fd, buf, sizeof(buf), 0);   // ← 阻塞在这
        ...
    }
}
```

**线程池的设计前提是"任务会结束，线程会回到队列"。**
而 `handle_client_read` 的平均执行时长 = 连接存活时长 = 几分钟到几小时。

于是：

```
worker 拿到 fd → 再也不回队列 → 池子里的可用 worker 减少
workers=4 → 第 5 条连接的任务永远排在队列里
```

**线程池退化成"有硬上限的 thread-per-connection"。**

## 4.2 三个缺陷是同一个人格

| 缺陷 | 表现 | 本质 |
|---|---|---|
| 并发度 = worker 数 | 第 5 条连接静默无响应 | 任务不结束 → worker 不归还 |
| 背压只能拒绝新连接 | 已有连接无法减速 | 没有"读到上限就返回"的能力 |
| 线程数 ≠ 连接数，但并发度 = worker 数 | 省了线程，锁死了能力 | 参数换了，架构没换 |

三条的根子都是 **`recv()` 是阻塞的**。所以：

> **修线程池不是办法，让任务变短才是办法。**
> **而让任务变短，只能靠非阻塞 IO + 事件驱动。**

## 4.3 一个容易忽略的推论

`try_run_one()` 是在这个认识下发明的：

```cpp
// reactor 在 epoll_wait 的间隙，自己从队列里拿一个任务执行
while (_running && _Pool.try_run_one()) { }
```

它让 reactor 线程不至于空等。但它的**安全前提写在注释里**了：

> 只有当池里全是"短任务"时才安全；混进一个阻塞任务（比如
> `while(true) recv` 的 `handle_client_read`），reactor 线程就会被卡死。

**也就是说：`try_run_one` 和 epoll 是一对，必须同时用。**
单独用 `try_run_one` 反而会让 reactor 被长任务拖死 —— 这是"半成品方案比没有更危险"的典型例子。

# 五、阻塞 vs 非阻塞：分水岭在哪

## 5.1 一行代码的差别，一个架构的差别

```cpp
// 阻塞
n = recv(fd, buf, len, 0);      // 没数据 → 线程睡眠 → 有数据才返回

// 非阻塞（O_NONBLOCK）
n = recv(fd, buf, len, 0);      // 没数据 → 立刻返回 -1，errno = EAGAIN
```

## 5.2 为什么 epoll 必须配非阻塞

这是新手最容易漏的一环。`epoll_wait` 告诉你"这个 fd 可读"，
**但读完这一批数据后如果不立刻停下，下一次 `recv` 就会阻塞**。

| 场景 | 阻塞 fd 的后果 |
|---|---|
| `epoll_wait` 说"可读"，但另一个线程先读了 | 你再 `recv` → **阻塞**，整个 reactor 卡死 |
| 你循环"读到 EAGAIN 为止" | **永远等不到 EAGAIN**（阻塞 fd 不会返回它），循环不退出 |
| `send` 时发送缓冲区满 | **阻塞**到发完，期间所有其他连接无人服务 |

第二条最要命：**epoll 的标准读法"读到 EAGAIN 才停"，
只有非阻塞 fd 才可能退出循环。**

## 5.3 一旦非阻塞，输出缓冲区就成了硬性要求

这是 README 里标的 P0 炸弹，现在能说明它为什么必然爆发：

```cpp
// main.cpp 现有的 send 循环
while (sent < len) {
    ssize_t n = send(fd, data + sent, len - sent, MSG_NOSIGNAL);
    if (n <= 0) {
        if (n < 0) perror("send");
        return;                 // ← EAGAIN 时静默丢弃剩余数据
    }
    sent += n;
}
```

- **现在（阻塞 socket）**：`send` 不会返回 `EAGAIN`，它会睡到发完 → 代码侥幸正确
- **改非阻塞后**：`EAGAIN` 是**常态**（对端慢、网络拥塞）→ 每次 `EAGAIN` 都丢掉消息尾部
  → 表现为"偶尔少几个字节"，没有任何报错，连接继续正常

**这是最恶劣的 bug 类型：静默的数据损坏。**

修法只有一个：**每连接一个写缓冲区**，`EAGAIN` 时把剩余数据存起来，
注册 `EPOLLOUT`，等可写时再冲刷。

> 而且这一步不只是 `EAGAIN` 的前置条件 —— 它同时是 **TLS 的前置条件**
> （`SSL_write` 也有 `WANT_WRITE`）。所以这一步无论如何不能跳。

# 六、reactor 怎么解决

## 6.1 核心思想：把"等"和"处理"分开

```
thread-per-connection：
   线程 = 等待者 + 处理者        （1 个线程 1 条连接）

reactor：
   reactor 线程 = 唯一的等待者，同时等所有 fd
   worker 线程  = 处理者，只处理"已就绪"的事件
```

一句话：

> **让一个线程问内核："这一万个 fd 里，哪些有数据？"
> 而不是让一万个线程各自问："我这个 fd 有数据吗？"**

```cpp
// 阻塞模型：线程问单个 fd，然后睡在它上面
n = recv(fd, buf, ...);

// epoll：线程问内核"谁准备好了"，睡在所有 fd 上
int n = epoll_wait(epfd, events, MAX_EVENTS, -1);
for (int i = 0; i < n; ++i) {
    // events[i].data.fd 就是有数据的那条连接
}
```

## 6.2 关键收益：任务变"短"了

| | thread-per-conn | 线程池（阻塞版） | epoll reactor |
|---|---|---|---|
| 任务是什么 | 整个连接的生命周期 | 整个连接的生命周期 | **一次就绪事件** |
| 任务时长 | 分钟~小时 | 分钟~小时 | **微秒~毫秒** |
| 任务结束 | 连接关闭 | 连接关闭 | **事件处理完立刻返回** |
| worker 归还 | ❌ 不归还 | ❌ 不归还 | ✅ **每次处理完就归还** |

**这一行是整个架构的分水岭**：

> 任务短了，线程池才真正成立。
> 任务短了，`try_run_one()` 才安全。
> 任务短了，`workers` 才等于"并行处理能力"而不是"并发连接数上限"。

**epoll 和线程池不是替代关系，是配套关系。** 线程池从来没写错，
它只是被喂错了任务。

## 6.3 新的并发度模型

```
thread 模型：并发连接数 ≤ 线程数 ≈ 40,000（内存上限）
pool 模型：  并发连接数 ≤ worker 数（通常是 4~16）
reactor：    并发连接数 ≤ RLIMIT_NOFILE（可调到 1,000,000+）
             并行处理能力 = worker 数（可调）
             ★ 这两个数字解耦了 ★
```

**"能同时持有多少连接"和"能同时处理多少请求"被彻底分开**，
这是 reactor 最本质的贡献。前两个模型里这两个数字是同一个。

## 6.4 验收标准

```bash

./test/test_03_pool_starvation.sh
  → pool: 第 3 条连接 recv=0, errors=1

# 改造后（epoll 模型）
# 期望：workers=2，1000 条连接全部正常 echo，mismatch=0
```

> **这就是这次架构升级的全部意义。**

# 七、代价：复杂度没有消失，只是转移了

必须诚实记录这一节，否则将来会被"reactor 更好"这个结论误导。

| 复杂度项 | thread 模型 | reactor 模型 |
|---|---|---|
| 一个问题一条线程 | ✅ 直观 | ❌ 状态机，难读 |
| 模块间共享数据 | ❌ 要加锁 | ✅ 单线程无锁 |
| 非阻塞带来的复杂性 | ✅ 不存在 | ❌ `EAGAIN` 到处都是 |
| 部分读写 | ✅ 不存在 | ❌ 必须有 rbuf/wbuf |
| 消息边界 | ✅ 不存在 | ❌ 必须自己处理粘包/拆包 |
| 调试 | ✅ 可以单步 | ❌ 事件驱动，断点难打 |
| 空连接成本 | ❌ 8 MB 栈 | ✅ 几十字节 |

**新增的具体工作量**（这也是为什么不能一步到位）：

| 工作 | 大概代码量 | 能不能省 |
|---|---|---|
| 非阻塞 fd 设置 | 5 行 | ❌ 不能 |
| 读循环 + `EAGAIN` 处理 | 20 行 | ❌ 不能 |
| **输出缓冲区** | 100 行 | ❌ **不能**（TLS 前置） |
| **消息边界/粘包处理** | 150 行 | ❌ 不能（要做客户端通信就必须） |
| 连接生命周期（`shared_ptr`） | 60 行 | ❌ 不能 |
| 空闲超时 / 连接上限 | 50 行 | ⚠️ 上公网前必须 |

**所以：reactor 不是"更简单的方案"，是"把 O(连接数) 的线程成本
换成 O(1) 的状态机复杂度"。** 这个交换在连接数大时极其划算，在连接数小时是负担。

# 八、决策速查表

## 8.1 什么时候该用哪个

| 场景 | 推荐 | 理由 |
|---|---|---|
| 连接数 < 几百，每连接持续处理 CPU 密集任务 | **thread / 线程池** | 代码简单，reactor 的复杂度不划算 |
| 连接数 > 1000，且大部分时间在等 IO | **reactor（epoll）** | 线程成本不可接受 |
| 大量短连接（HTTP 风格） | **reactor** | 连接建立/销毁比处理还贵 |
| 阻塞操作（磁盘 IO、DNS） | **reactor + 小线程池** | nginx 就是这么做的 |
| 需要极简实现、可靠性优先 | **thread** | 少一层状态机，少一类 bug |

## 8.2 nginx 的真实架构（重要参考）

```
master process（只管管理，不处理请求）
  ├── worker process 0   ← 单线程！独立 epoll，处理自己那份连接
  ├── worker process 1
  ├── worker process 2
  └── worker process 3
      通常 = CPU 核数，用 SO_REUSEPORT 各自抢连接
```

**关键认知**：nginx 的 worker 是**单线程事件循环**，没有"线程池处理连接"这回事。

nginx 的线程池**只干一件事：卸载阻塞操作**（磁盘 IO、`getaddrinfo`）。
源码里 epoll 循环的唯一例外就是磁盘读，因为页缓存未命中时要等 5ms，
这 5ms 不能让 worker 干等 → 丢给线程池 → 立刻回去 `epoll_wait`。

**对照本项目**：

| 组件 | nginx 里的角色 | 本项目现状 |
|---|---|---|
| `IoThreadPool` | 只用于阻塞操作卸载 | ⚠️ 现在用来"处理连接"，属于异端用法 |
| `EpollServer` 单 reactor | worker 的雏形 | ✅ 正在写，方向正确 |
| 多 reactor + `SO_REUSEPORT` | nginx 真正的架构 | ⬜ 阶段 4 |
| `BlockingQueue` | nginx 用无锁 ring + 信号 | ✅ 教学用可接受 |

**`try_run_one()` 在 nginx 里没有对应物** —— 它是混合模型
（Redis 6 多线程 IO、Envoy worker 模型都在这条路上）。
这条路没错，但要知道它不是 nginx 路线。

## 8.3 一页速查

```
阻塞 recv        → 线程被绑死在一条连接上 → 并发度 = 线程数
线程池 + 长任务  → 并发度 = worker 数    → 静默不可用
```

| 现象 | 根因 | 解法 |
|---|---|---|
| 第 N+1 条连接无响应 | worker 被长任务占死 | 任务变短（epoll） |
| 无法给快客户端减速 | 阻塞 socket 无法表达"读了但处理不了" | 非阻塞读 + 读配额 |
| 线程数随连接数增长 | 1 连接 = 1 线程 | epoll 让 1 线程管 N 连接 |
| 非阻塞后数据偶尔缺失 | `send` 遇 `EAGAIN` 直接 return | 输出缓冲区 |
| 收到半条消息 | TCP 是字节流，无消息边界 | 长度前缀 + 读缓冲区 |
| `stop()` 唤不醒 `epoll_wait` | epoll 只等事件，不看 fd 有效性 | eventfd |
| `epoll_wait` 前用 `sleep_for` 退避 | 睡的时候不监听 | 用 timeout 参数 |
