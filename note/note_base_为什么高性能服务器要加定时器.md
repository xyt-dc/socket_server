在高性能网络服务器中，定时器（Timer）是和网络事件循环（Reactor）同等重要的核心支柱。
如果说 epoll 解决了“外部有数据来时通知我”，那么定时器解决的就是“外部没动静，但时间到了必须通知我”。没有定时器的服务器，在真实生产环境中很快就会因为僵尸连接、死锁请求或内存泄漏而崩溃。
结合你前面设计的自定义协议和 Reactor 架构，高性能服务器使用定时器的四大核心功能如下：

1. 踢掉“僵尸连接”（Idle Connection Kickout）——最核心功能

• 痛点：互联网环境极其复杂，客户端可能随时断网、拔网线、手机进电梯或直接杀进程。此时客户端根本发不出 TCP 断开包（FIN），服务端如果不主动检测，这个 Connection 对象和文件描述符（FD）就会永远留在内存里。几万个断网用户积累下来，服务器内存和端口就会被彻底耗尽。
• 定时器功能：每隔固定时间（如 5 秒或 10 秒）检查一遍，只要某个连接超过 45 秒没发过任何数据（包括你前面设计的 Ping 心跳包），定时器就会强制触发 Close()，关闭 Socket 并释放内存。

2. RPC / 异步请求超时控制（Request Timeout）

• 痛点：你的客户端或网关发出了一个带 Seq = 1001 的请求，在回调表里注册了等待回调。但如果对端服务器卡死了，永远不回包，这个 Seq = 1001 的回调对象就会永远挂在内存里泄漏，调用方也会无限期死等。
• 定时器功能：在发请求、把 Seq 存入等待表的同时，顺手挂一个 3 秒（或 5 秒）的延迟定时器。如果 3 秒内回包到了，就取消定时器；一旦 3 秒到了还没回包，定时器触发，自动从表中删除 Seq = 1001，并给业务层返回 ErrorCode::Timeout。

3. 定时发送心跳与断线重连（Keep-Alive & Reconnect）

• 功能：
	• 保活：如果连接处于空闲状态超过 15 秒，定时器自动触发发送一个 PingReq 包（防止中间的运营商防火墙/NAT 网关因为连接太久没流量而偷偷掐断 TCP 映射）。
	• 重连退避：当客户端连接断开后，不能在 while 循环里疯狂重连（会把服务器打死），而是用定时器实现指数退避重连（第 1 秒重连一次、失败等 2 秒、再失败等 4 秒……）。

4. 业务层周期性任务与状态刷新（Periodic Tasks）

• 延迟任务：例如玩家下线后角色在原地保留 10 秒再消失、订单创建后 15 分钟未支付自动取消。
• 批量刷盘 / 监控统计：每隔 1 秒统计一次当前的 QPS（每秒请求数）和活跃连接数写入监控日志；或者把内存里的热点数据每隔 5 秒批量异步写入一次数据库，大幅减轻数据库压力。

💡 高性能服务器是如何实现定时器的？（零额外线程黑科技）

在你的 Sub Reactor（epoll 事件循环） 中，通常不需要专门开一个独立线程去跑 sleep 死循环（开独立线程会引入多线程抢锁问题，破坏你 Connection 的无锁安全）。
工业界（如 Muduo、Nginx）有两种极其优雅的融入方式：
1. 利用 epoll_wait 的最后一个参数（超时时间 timeout_ms）：
	• 每次进入 epoll_wait(epfd, events, max, timeout) 之前，看一眼定时器容器里最近一个即将到期的任务还有多少毫秒，把这个时间传给 timeout。如果期间有网络包，立刻处理网络包；如果一直没包，时间一到 epoll_wait 准时返回，顺手把到期的定时任务全执行了。
2. Linux 专属神器：timerfd：
	• Linux 内核可以把定时器变成一个文件描述符（timerfd_create），直接塞进 epoll 里和普通 Socket 一起监听。时间一到，内核就像收到网络数据一样触发 epoll 可读事件，整个 Reactor 循环彻底统一成纯事件驱动。
*(注：当并发连接数达到十万、百万级时，普通的红黑树 std::map 增删定时器会有 \(O(\log N)\) 开销，此时高性能服务器会采用**时间轮（Timing Wheel）*算法，把定时器的插入和删除全部降到 O(1) 常量级时间复杂度。)
你的服务器目前是跑在 Linux 环境下吗？如果你想把定时器直接整合进你的 Sub Reactor 事件循环里，我可以帮你写一个基于 timerfd + 时间轮（或 std::multimap） 的无锁定时器管理器，让每个 Sub Reactor 线程都能安全高效地管理成千上万个连接超时。

# 附：落到**本项目**时要修正的三处

上面那部分是通用概论，方向和术语都对。但把它套到这套代码上时，
有三处结论**必须改**，否则实现出来会出线上级故障。每处都有代码依据。

## 修正一：定时器的适用范围已经收窄——只做 epoll 和主从 reactor

原文没有区分模型。本项目里三个模型的分工**不是并列的**：

| 模型 | 定位 | 做定时器吗 |
|---|---|---|
| `thread`（one-per-conn） | **基准实现**，用来对照验证别的东西 | ❌ 不做 |
| `pool` | 第三种服务器到主从 reactor 之间的**过渡板** | ❌ 不做 |
| `epoll` | 目标形态的单线程版 | ✅ **做** |
| 主从 reactor（第四种） | 目标形态；`pool` 的能力最终被吸收进它的 Sub Reactor worker 池 | ✅ **做** |

这不是偷懒，而是**两个模型的收尾机制根本不同**，值得单独说明：

`src/server/tcp_server.cpp:57` 用的是

```cpp
return accept(_listen_fd, (struct sockaddr*)&server_addr, &len);
```

**`accept()` 而不是 `accept4(..., SOCK_NONBLOCK)`**，所以 pool / thread 的
client fd 是**阻塞**的，worker 正阻塞在 `recv` 上。这时踢掉一条连接：

| 操作 | 对「另一个线程正阻塞在该 fd 的 recv」 |
|---|---|
| `close(fd)` | **不唤醒**。fd 引用计数还挂在 syscall 上，worker 永久挂死；之后 close 到被复用的 fd 还会误伤新连接 |
| `shutdown(fd, SHUT_RDWR)` | **立刻唤醒**，`recv` 返回 `0`，worker 自己走正常收尾 |

而 `epoll` 用的是 `Epoll_server.hpp:188`：

```cpp
int cfd = ::accept4(_listen_fd, nullptr, nullptr, SOCK_NONBLOCK | SOCK_CLOEXEC);
```

**fd 本来就是非阻塞的**，`del_and_close(fd)` 就是全部动作。

所以：

> 那条「定时器线程只 shutdown 绝不 close」的规则**对 epoll 不适用**，
> 它是 pool/thread 的问题。范围收窄之后，整段讨论随之作废。
> 唯一需要记住的是**为什么**不做 pool：不是因为它不重要，
> 而是它要被主从 reactor 取代，在它身上投资定时器是浪费。

顺带纠正一个曾经影响判断的误解：**pool 里泄漏的不是 fd，是被阻塞的 worker 线程。**
`workers=2` 遇到 2 条死连接就直接全饿死，第 3 条正常请求永远无人处理
（README §九「A 饿死」测的就是这个）。
—— 这正是为什么它需要 `shutdown`，也正是为什么它留给了主从 reactor 去解决。

## 修正二：45 秒解决不了「手机断网」，而且会踢掉 chat 用户

原文 1 里的场景描述 ——「客户端断网、拔网线、手机进电梯，发不出 FIN」
—— 是**完全正确**的。但结论「超过 45 秒没数据就踢」解决不了它，
反而会引入新问题。

### 为什么解决不了

从服务端视角看，下面两件事**在字节层面完全一样**：

```
场景 A：用户正在看消息，暂时没打字     → 正常，不该踢
场景 B：用户手机进电梯，信号断了       → 已死，该踢
```

两种情况服务端看到的都是：`recv` 一直 `EAGAIN`，缓冲区没新字节。
**定时器只能回答「多久没动静」，不能回答「对端还在不在」。**
回答后者必须**主动发包并等回应** —— 那就是 Ping 心跳。

原文本来的第 3 条「定时发送心跳」才是真正的解法，它和超时是**两层**：

| 机制 | 阈值 | 作用 |
|---|---|---|
| Ping 心跳 | 25s | **发现断网**，主检测 |
| 空闲超时 | ≥ 2.5× 心跳 ≈ 75s | 兜底：防 fd 累积、防 slowloris |

### 45 秒对 chat 是错的

`chat` 业务里「用户不说话」是**正常状态**。
按 45s 踢人：用户打开 App 看 50s 消息 → 连接被断 → 别人发的消息推不过来。

**chat 的空闲超时应在 300s 量级**，离线检测交给 Ping/Pong。
基础设施先做好，阈值等 `chat` 落地再定，且必须可配置。

## 修正三：本项目**不需要** timerfd，也暂时不需要时间轮

原文的「零额外线程黑科技」两条建议里，第一条（用 `epoll_wait` 的 timeout）
本项目**已经在用了**。依据 `src/mthread/Epoll_server.hpp:25,69`：

```cpp
static constexpr int kWaitTimeOut = 100;
...
ssize_t n = _epoll.get()->wait(event_poll, kWaitTimeOut);
```

主循环本来就每 100ms 醒一次。所以：

- **不需要 `timerfd`** —— 那块基础设施的钱已经付过了
- 代价是空闲时每秒 10 次无谓唤醒，可接受

时间轮同理，看真实规模：

| 连接数 | 扫描法每 tick 成本 | 需要堆/时间轮吗 |
|---|---|---|
| 500（本项目现状） | ~500 次 map 查找，几十微秒 | ❌ 不需要 |
| 10,000 | ~10 万次，几百微秒 | ⚠️ 可选 |
| 100,000 | ~100 万次 | ✅ 需要 |

**现在上时间轮是负优化**：多一个结构、多一处一致性维护、
还要求在每次 add/remove 连接时同步维护轮内位置。

## 通用概论里没提到、但本项目必踩的三个坑

### 坑 1：必须用 `steady_clock`

`system_clock` 是 `CLOCK_REALTIME`，会被 NTP 调整：

- **调慢** → `now - last_active` 变负 → 永不超时 → fd 慢慢泄漏
- **调快** → `now - last_active` 突然巨大 → **所有连接同一秒集体断开**

第二种在线上表现为「每天凌晨 3 点全体掉线」，本地测试永远复现不了。
`steady_clock` 走 `CLOCK_MONOTONIC`，单调递增，专为测量间隔设计。

### 坑 2：刷新点必须覆盖 send 成功

| 时机 | 证明什么 |
|---|---|
| `recv` 返回 `n > 0` | 对端应用**还在发** |
| `send` 成功发出字节 | 对端应用**还在收** |

只刷读的话，「只推送不收请求」的连接（订阅/通知类业务）
无论服务端推得多勤，时间一到照样被踢。
所以「空闲」的语义必须是 **双向都没流量**。

### 坑 3：不能在遍历 `_conns` 中 `erase`

`del_and_close` 内部就是 `_conns.erase(fd)`。
在 `for (auto& kv : _conns)` 里 erase 会让迭代器失效。

必须两步：持锁收集过期 fd 到 `vector<int>` → **放锁** → 逐个删除。
放锁是必需的：`send_wbuf` / `handle_read` 都要拿同一把 `_mtx`，
持锁遍历 500 条连接会把业务线程的 `send` 全阻塞。
（这跟 `tlv_codec` 那次讨论的结论是同一条规律。）

`close()` 一行就能让连接消失，但错误的实现同样能让它消失。
所以四个阶段两两成对：

| 阶段 | 断言 | 抓什么缺陷 |
|---|---|---|
| `[1] die` | 连上不说话 → 必须被断开 | 超时根本没生效 |
| `[2] alive` | 持续发 → 一次都不能断 | 刷新点漏了 send 侧 |
| `[3] 混合` | 1 死 + 5 活共处 → 死的被清、活的零误伤、进程不崩 | 遍历中 erase / 持锁删除 |
| `[4] 边界` | 0.75× 间隔持续发 → 不能断 | 基准取了「上次扫描时间」 |

`[3]` 是 epoll 特有的关键阶段：扫描式定时器最容易在

```
die   → {"ok": false, "close_kind": "still_alive", "elapsed_s": 7.002}
alive → {"ok": true,  "sent": 8, "recv": 8, "dropped": 0}
```

两条都符合预期 —— 证明探针不是「永远 PASS」的假绿。
